## 2. Architecture for Phase 1

- **Auth.** `src/auth/`: an `AuthProvider` over Supabase Auth (Google, redirect flow) exposing `session`, `member` (the active `members` row for the user) and `signOut`. In local mode a `LocalAuth` picks the member (dev picker in the More menu; `__uaTest.signInAs(memberId)` in tests). The signed-in member is the actor of every mutation.
- **Repository selection.** `VITE_DATA=local|supabase`. LocalRepository (Dexie) serves dev-without-backend, unit, component and local e2e tests; SupabaseRepository serves staging, prod and live tests. Both implement the full interface and both refuse writes to another member's data (local in code via the same `can()`, Supabase via RLS).
- **Permissions.** `src/domain/permissions.ts`: `can(actor, action, target)` mirrors the matrix; `useCan()` reads the signed-in member. Every editing control and edit shortcut goes through it; the repositories call it too, so local mode catches leaks.
- **Schema** (`supabase/migrations/`): `members` (auth user id, email, name, slug, is_admin, active), `sheets`, `columns`, `stages`, `rows` (identity keys as generated columns: E.164 phone, lowercased email, LinkedIn slug, normalised name and company; `pg_trgm` indexes), `tags` (created_by), `row_tags`, `history`, `row_links` (source row, target row or free text, kind), `files`, `not_duplicate_pairs`. Every owned table has `owner_id`; `updated_at` and `rows.last_touch_at` maintained by triggers; `deleted_at` on rows, columns and sheets. RLS on every table through `current_member()`. Security-definer functions: tag guard, `search_rows`, `purge_trash`.
- **Realtime.** One channel per viewed sheet (rows, history, row_tags) plus members and sheets; events patch the TanStack Query cache without moving focus or scroll.
- **Offline.** `useConnection()` (browser online state + Realtime channel status); a quiet notice in the header area; mutation hooks refuse while offline. No write queue.
- **Undo and redo.** A session command stack (`app/undoStore.ts`): every mutation registers an inverse built from repository operations; Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z. The Phase 0 undo toasts become views onto the same stack.
- **Deploy and CI.** Static build; previews against staging, manual production workflow (migrations, then deploy). A `db` CI job starts local Supabase and runs pgTAP, contract and live e2e. Hosting provider: see question Q1.

## 5. Questions for the founders (asked at the end of M1.0)

- **Q1 Hosting.** Vercel's free Hobby plan is for personal, non-commercial use only, and UA is a company. Phase 1 needs only static hosting (Supabase does auth, data and Realtime; backups run in GitHub Actions), and Phase 2's server code can run as Supabase Edge Functions (free tier). Options: keep Vercel Hobby and accept that its terms do not cover this use, or use Cloudflare Pages (free, commercial use allowed, preview deploys per branch). Recommendation: Cloudflare Pages.
- **Q2 Repository.** The brief asks for a private `ua-crm` repository. Recommendation: rename the existing `Dawar13/UA_CRM` to `ua-crm` and make it private (keeps history, CI and baselines). Private repositories get 2,000 free GitHub Actions minutes a month; Phase 1 CI with the database job is about 12 minutes a run, so about 160 runs a month. CI is kept lean (cancel superseded runs, path filters for docs-only changes) and usage is reported at each milestone.
- **Q3 Docker.** The local Supabase stack runs in Docker Desktop. Docker must be running on this machine, and the first start downloads about 2 to 3 GB of images (unneeded services such as Studio and the image proxy are excluded).
- **Q4 Leftovers from Phase 0:** the Customers turnover bands (< ₹50 Cr, ₹50–250 Cr, ₹250–1,000 Cr, > ₹1,000 Cr) and the `buffers` package without a licence that ExcelJS pulls in (export needs ExcelJS).

## 6. Order of work and risks

1. M1.0 (this plan and `CLAUDE.md`), then the questions above.
2. M1.1 steps 1–2 (local stack, migrations) can start as soon as Docker runs; step 3 waits for the founder setup.
3. Local-mode work that needs no backend (permissions in the domain, view only, editing, quick-add parser, dedupe scorer) proceeds on LocalRepository in parallel and is wired to Supabase as soon as it exists.

Risks: free-tier pausing of the staging project (the daily job pings both projects); Realtime and RLS performance at 2,000 rows (measured in the perf layer); GitHub Actions minutes on a private repository (Q2); the 1 GB Storage limit (file sizes capped at 10 MB, usage reported).
